## 2.7.0

- fix: `WorkerTestUtils.work()` and `workScheduled()` can now find a queue built under a `Cluster` connection when called with a `queue` name. The internal comparison that matched a requested name against a running queue opened a brace for the cluster case (`` `{${name}` ``) and never closed it, so it could never equal a queue's real cluster-mode name (`` `{${name}}` ``, both braces) — the comparison silently failed, `work({ queue })`/`workScheduled({ queue })` iterated no queues, and the call returned having worked nothing rather than raising an error. Both now resolve the queue's expected name through `nameToRedisQueueName`, the same function the package itself uses to build a queue's Redis name, so the two sides can no longer disagree — including under a `VITEST_POOL_ID`-suffixed parallel-test name, which the old cluster branch also skipped. `queueNamesMatch` is now exported from `WorkerTestUtils` as the single predicate both methods share.

- fix: a debounced delayed job — one enqueued with a `jobId` — is no longer skipped, and the deduplication key now expires before the job it guards runs. The key's lifetime was pinned equal to the delay, but the two deadlines are measured from different clocks: the job's fire time comes from the producing process, the key's expiry from Redis at the moment the enqueue lands there, and promotion out of the delayed set from the worker. The key could therefore outlive its own job, and a call arriving in that gap found nothing to replace, got the old job's id back, and enqueued nothing — after the job had already run. The key's `ttl` is now the delay minus one second (floored to a positive integer), so that — as long as the enqueue round trip and any clock skew together fit inside that one second, which is the premise the rest of this bullet is about — a live key means a run is still pending: every call either slides the timer or starts a new one. **This changes behaviour for existing callers.** A burst that previously collapsed into one run, and could lose the last call in it, may now produce two runs instead — an extra run rather than a missed one, which is the trade a debounce wants. Calls landing in the last second of the window — between the key's expiry and the fire time — stop collapsing, and that dead band is a flat second whatever the delay: 20% of the window at the five-second floor, 0.03% at an hour. A caller whose cadence happens to fall inside it loses the debounce entirely rather than occasionally: with `{ seconds: 5 }`, calls at 0.0, 4.5 and 9.0 each produce a run, where under the old `ttl` equal to the delay they collapsed into one. The lever is the delay — the margin does not grow with it, so **longer delays are strictly cheaper**, and a caller that cares about collapsing and can tolerate a later run should widen the delay rather than tighten it. Separately, whenever promotion stalls — a rate-limited workstream, a paused or absent worker, a long job ahead of it at `concurrency: 1`, a deploy with no worker running — every call for the length of the stall becomes its own delayed job. The window is narrowed, not closed: the one-second margin has to cover the enqueue round trip _and_ clock skew together, so a Redis failover, an ioredis reconnect that buffers the command in its offline queue, or a fork pause during `BGSAVE` can consume it on its own even with perfectly synchronised clocks, and where several producers share a `jobId` the margin must hold for the worst-clocked of them, since the fire time comes from whichever process made the last call. There is no knob and no restore recipe: the margin is not configurable, nothing exposes the old lifetime, and an application that needs it must pin 2.6.0 or drive BullMQ directly through `background.queues`. A suite that asserts the enqueued job options will need its `ttl` expectations updated.
- `jobId` is a deduplication key, not the BullMQ job id, and the TSDoc now says so along with what the mechanism is for: a debounce, in which repeated calls within the delay window collapse into one run that happens after the last of them. `queue.getJob(jobId)` does not resolve a debounced job through it; the key lives in Redis under `<prefix>:<redis queue name>:de:<jobId>`, where the redis queue name is derived per connection and is not the queue name you configured. A resolved `await` on a delayed, deduplicated enqueue means a run is pending after that call — the timer was slid or started — not that the call created a job of its own; a swallowed call emits no event and carries no flag, so it cannot be instrumented around. `backgroundWith`'s `@param opts.delay` also picked up the "given as at least one of `seconds`, `minutes`, `hours` or `days`" clause that `backgroundWithDelay`'s `@param delay` already carried, so the two no longer disagree on what the field accepts. Documentation only; no behaviour change beyond the fix above.
- **breaking at runtime: a delayed job carrying a `jobId` now requires a delay of at least five seconds, and is refused at enqueue otherwise.** `backgroundWithDelay({ seconds: 4, jobId: 'my-job' }, …)` and `backgroundWith({ delay: { seconds: 4, jobId: 'my-job' } }, …)` throw, as does a `jobId` carried by a zero, negative, `NaN`, `Infinity` or out-of-safe-range delay — shapes that work on released 2.6.0 and that this repository's own specs used. An **empty** `jobId` is refused the same way, at any delay: the type admits it and it is what a key built from a missing value looks like, but it is not a usable deduplication key (BullMQ refuses it too), and the alternative was to enqueue a delayed job with no key and no signal — the silent no-op this bullet exists to remove. Below five seconds a debounce window is the same order as the time it takes a worker to pick a job up, so there is nothing left to debounce; refusing is deliberate, in preference to silently raising the delay or deduplicating nothing. The floor applies **only** when a `jobId` is present: a short, zero or negative delay without one is unaffected. There is no opt-out and nothing warns at compile time, and the thrown error class is not exported, so this surfaces as a throw at the enqueue call site. The check runs before the test-mode short circuit, so a suite running under the default `testInvocation: 'automatic'` raises it exactly as production does, and any fixture pairing a sub-five-second delay with a `jobId` will go red on upgrade. Five seconds is a floor rather than a recommendation: the dead band described in the bullet above is a flat second, so it costs a fifth of the window there, and a delay that sits at the floor deduplicates nothing whenever promotion stalls for longer than four seconds — which a rate-limited workstream does by design.
- **breaking at compile time: a delay object now requires at least one of `seconds`, `minutes`, `hours` or `days`.** `backgroundWithDelay({}, …)`, `backgroundWithDelay({ jobId: 'my-job' }, …)`, `backgroundWith({ delay: {} }, …)` and `backgroundWith({ delay: { jobId: 'my-job' } }, …)` stop compiling, with or without a `jobId`: a delay with no duration delayed nothing, and a `jobId` with no duration deduplicated nothing. Any call whose duration fields are all optional _at the type level_ is rejected too, even where one is always set at runtime — an unavoidable consequence of requiring at least one of four. That covers more than a literal: a variable typed with optional durations (`const opts: { seconds?: number; jobId?: string }`), a spread of this package's own all-optional duration type (`backgroundWithDelay({ ...dur, jobId: 'x' }, …)` where `dur: DelayedJobDuration`), and — the shape most likely to be in working code — a duration read from configuration, an environment variable or a nullable column (`backgroundWithDelay({ seconds: maybeSeconds }, …)` where `maybeSeconds: number | undefined`). All three compiled on 2.6.0, under `exactOptionalPropertyTypes` both true and false (the flag changes only the error code). The fix is to pin a duration at the call site — narrow the value first (`if (maybeSeconds === undefined) return`, or a default) and pass it as a required field. Naming the option type instead is not available: `DelayedJobOpts` is not exported, so a consumer restructures the call rather than importing a type. There is no runtime equivalent of this check, so a JavaScript consumer sees nothing here; the first thing they meet is the five-second throw above.
- **breaking at runtime: asking for workers — `background.work()`, or a direct `background.connect({ activateWorkers: true })` — now starts them in a process that had already connected, and raises instead of returning quietly when that process has no worker connection.** `connect()` builds each process's queues once and returned early on any later call, and worker activation used to be part of that body — so in a process that had connected first, for any reason, a later request for workers reached the guard, returned, and built nothing: no workers, no error, no log line. Activation is now separate from connection, and both `work()` and `connect({ activateWorkers: true })` build the workers from what the first `connect()` recorded, whichever call came first. Everything below is written in terms of `work()`, which is how this package itself asks for workers, but it applies identically to an application that calls `connect({ activateWorkers: true })` directly. Two shapes are affected, and both are quiet today. A process that connects as a producer and then works its own jobs — a webserver that also runs `work()`, or a worker entrypoint that registers a scheduled service before calling `work()`, since `.schedule()` connects — silently processed nothing, stayed alive and passed health checks; it now comes up with its workers, which is the point of the change, and a fleet sized on the assumption that such a process consumed nothing will start consuming on upgrade. The second shape is the one that breaks on boot: a process that calls `work()` with no `defaultWorkerConnection` resolvable (commonly a web process where the worker connection is only set when a worker-service environment variable is, and the schedulers happen to register first) used to return silently and now throws `ActivatingBackgroundWorkersWithoutDefaultWorkerConnection` at the `work()` call site. That class is not exported, so it cannot be caught by class; the remedy is to configure a `defaultWorkerConnection` in that process, or not to call `work()` in it. Nothing changes for the ordinary two-process deployment, where the worker entrypoint's first background call is `work()`. One further consequence for suites and scripts: after this change, code that connects and then calls `background.work()` directly constructs real BullMQ `Worker` objects holding worker Redis connections that nothing closes until `shutdown()`. The documented test route does not go through it — `WorkerTestUtils.work()`, `workScheduled()` and `clean()` all call `background.connect()` with no arguments and never `work()`.
- `rateLimit` on a named workstream now rate limits on open-source BullMQ, not only BullMQ Pro. It is written as BullMQ's worker `limiter` option (https://docs.bullmq.io/guide/rate-limiting), which is enforced per queue: every one of the workstream's `workerCount` workers, in every process running it, shares one counter in Redis, so `{ max: 1, duration: 1000 }` means one job per second for the workstream as a whole. It composes with `concurrency` (how many jobs each worker runs at once vs. how many may start per window). Previously `rateLimit` was written only as Pro's group limit, so on open-source BullMQ it silently did nothing. `rateLimit` remains a named-workstream option only; the default workstream carries every other kind of work and deliberately does not take one. Give each rate-limited external service its own named workstream.
- fix: `priority` on a `backgroundJobConfig` now takes effect on a named workstream — and on any job given a `groupId` — without BullMQ Pro. A job's priority was written at the top level of the BullMQ job options, where open-source BullMQ reads it, only when the job had no group id; where one was present the priority was written _instead_ inside `group`, which is a BullMQ Pro option that open-source BullMQ stores but never acts on: it ignores `group` entirely for scheduling, so a priority living only there ordered nothing. Every named-workstream job carries a group id — the workstream name — so on open-source BullMQ `{ workstream: 'snazzy', priority: 'urgent' }` enqueued at BullMQ's default priority, and `priority` on such a class, or a `backgroundWith({ priority })` override of it, silently did nothing. The priority is now written at the top level on every job, with the Pro group priority written alongside it rather than in place of it. A job carrying no group id at all is unaffected: it never had one and always carried a top-level priority. That is the overwhelmingly common case — a class whose `backgroundJobConfig` names no `workstream`, `queue` or `groupId` — but it is narrower than "anything on the default workstream": a `backgroundJobConfig` of `{ groupId: 'someGroup' }` with no `queue` routes to the **default** queue and still carries a group id, so it moves from `waiting` to `prioritized` exactly as a named-workstream job does. **This changes behaviour for existing callers on open-source BullMQ**, and in the intended direction: jobs on a named workstream begin to be ordered by the priorities their classes already declare, so a workstream mixing priorities will no longer work strictly in enqueue order. It also moves such jobs from BullMQ's `waiting` set into its `prioritized` set — psychic-workers maps even `'default'` to a real BullMQ priority (2) rather than to no priority (0), so this applies to every workstream job, not only the explicitly prioritized ones. Nothing in this package reads `waiting` alone (`WorkerTestUtils.clean()` drains both), but an application's own monitoring, dashboards, or specs that count `getWaitingCount()` or assert a job's state on a named workstream will need to account for `prioritized`. On BullMQ Pro the group priority is unchanged and a top-level job priority is now set in addition, which under Pro orders jobs within a group where the group priority orders the groups against each other; inferred from Pro's documentation, not verified against an installed Pro build. `group` is still written on open-source BullMQ, and "never acts on" is not "discards": BullMQ passes option keys it does not recognise straight through when it serialises a job, so `group` is persisted in the job's `opts` hash in Redis, comes back on `job.toJSON()` and `queue.getJob()`, and is visible in a dashboard's job inspector — on every workstream job, at a small but real per-job storage cost alongside the priority accounting below. The precedence between this priority and a consumer's own queue defaults is now the same for grouped and ungrouped jobs: an explicit `backgroundJobConfig.priority` — and psychic-workers' `'default'` of 2 in the absence of one — is passed as a call option, and BullMQ merges queue defaults first and call options second, so it overrides a `priority` set in `defaultBullMQQueueOptions.defaultJobOptions`. Ungrouped jobs already behaved this way; grouped jobs sent no top-level priority before this change, so the queue default applied to them and now does not. For consumers who supply their own `providers.Queue` subclass: an ungrouped job's options object handed to `.add` no longer carries an own `group` key — previously it carried `group: undefined`. The persisted job in Redis is unchanged (`Object.hasOwn(job.opts, 'group')` is `false` both before and after, since BullMQ does not store the undefined value), so this is observable only by a subclass intercepting `.add` and inspecting the argument. One cost worth knowing on a very high-throughput workstream: moving jobs out of the `wait` LIST and into the `prioritized` ZSET is more expensive in Redis — measured over 20,000 jobs at roughly 97 bytes per job in the prioritized ZSET against roughly 3.8 bytes per job in the wait LIST, with O(log N) rather than O(1) enqueue and dequeue on the queue index and one extra `INCR` per add. Modest, and with no effect on correctness or on the per-job data itself.
- **fix: a scheduled (cron) job now carries the `priority` from its service's `backgroundJobConfig`, and this changes behaviour for existing callers.** `BaseScheduledService.schedule()` has always routed on that config — it picks the queue from `workstream`, `queue` or `groupId` — but it dropped the priority, so every cron job was registered with BullMQ's job scheduler at no priority at all. The priority is now written into the scheduler's job template, so every run it produces carries it. **On upgrade, every existing scheduled job moves from BullMQ's `waiting` set into its `prioritized` set**, the same move the bullet above describes for workstream jobs and for the same reason: psychic-workers maps even `'default'` to a real BullMQ priority (2) rather than to no priority (0). That move matters for more than the set name. BullMQ drains the `wait` LIST completely before it reads the prioritized ZSET — `moveToActive-11.lua` does an `RPOPLPUSH` off `wait` first and reaches the sorted set only once that list is empty — so a priority-less cron job was fetched ahead of every prioritized job on the same queue, `urgent` ones included, however long they had already been queued and however recently the cron job was added. An application whose scheduled service and backgrounded service share a queue therefore had its cron runs preempting the work it had explicitly marked urgent; the two are now ordered against each other by the priorities the classes already declare. An application that passes its own `priority` through `scheduleOpts` is unaffected: caller-supplied options are applied last and still win. What wins is a caller-supplied _value_, not a caller-supplied key — an explicitly undefined one (`scheduleOpts: { priority: maybePriority }`, the shape an options object takes when it is built from a config value, an env var or a nullable column, and one the BullMQ type admits) leaves the `backgroundJobConfig` priority in place rather than erasing it. Every other undefined-valued key in `scheduleOpts` is dropped the same way, which is what BullMQ does with them anyway. As with workstream jobs, an application's own monitoring, dashboards or specs that count `getWaitingCount()` or assert a scheduled job's state will need to account for `prioritized`.
- one path still puts a job ahead of a higher-priority one, and it is not one an application can configure away: BullMQ's stalled-job recovery. When a worker dies or loses its lock, `moveStalledJobsToWait` returns the job to the `wait` LIST unconditionally — it never reads the priority the job still carries — and BullMQ drains that list before it reads the prioritized ZSET. So a recovered job is fetched ahead of every prioritized job on its queue, `urgent` ones included, whatever priority the recovered job itself carries. This is upstream BullMQ behaviour rather than anything this package does, but it is new in practice: before these changes psychic jobs sat in `wait` anyway, and now that they sit in `prioritized`, recovery is the exception. It is also the reason `waiting` is no longer a reliable proxy for "carries no priority" — a stalled psychic job reports `getState() === 'waiting'` with its `opts.priority` intact, so monitoring that infers one from the other will be wrong for the length of the recovery. The inversion is transient, clearing as soon as the recovered job is picked up, and `maxStalledCount` bounds how many times a single job can go around the loop.
- rolling upgrades, for both of the priority changes above: jobs enqueued by 2.6.x carry BullMQ priority 0 and sit in the `wait` LIST, and BullMQ drains that list before it reads the prioritized ZSET. So for the length of the deploy window — until the pre-upgrade backlog clears — every job the upgraded code enqueues, `urgent` ones included, is fetched behind every job the old code left behind, whatever order the two were enqueued in. The inversion is bounded and clears on its own as that backlog drains, and nothing is stranded: nothing in this package reads `waiting` alone, and `WorkerTestUtils.clean()` drains both sets (`queue.drain(true)`, which removes the wait/paused LISTs and the prioritized ZSET alike). An application that cannot tolerate that window can drain the queue before rolling the new version out.
- on BullMQ Pro, `rateLimit` now sets the queue `limiter` in addition to the group limit it already set. For that workstream's workers the queue `limiter` takes precedence over a global `defaultBullMQWorkerOptions.limiter`, and it caps any per-group limit raised above `rateLimit` with `setGroupRateLimit`. Inferred from Pro's documentation; not verified against an installed Pro build.
- `rateLimit.max` and `rateLimit.duration` are now both required whenever `rateLimit` is given (`rateLimit?: { max: number; duration: number }` on `PsychicBackgroundWorkstreamOptions`). A partial `rateLimit` never rate limited on either build (open-source BullMQ does not validate the limiter and breaks the job fetch when `duration` is unset), and it is now a compile error rather than a silent no-op, so an application upgrading with a partial `rateLimit` will see a type error in that PR. A `rateLimit` that still reaches `connect()` without a positive integer `max` and `duration` (missing or mistyped from a JavaScript config or a cast, say, or a fractional or oversize value the `number` type admits) now fails `connect()` with an error naming the workstream and the field, before any queue or worker is built, instead of breaking every job fetch on that workstream with a BullMQ Lua error that never names `rateLimit`, or, for a fractional `duration` that open-source BullMQ floors to 0ms, silently rate limiting nothing.
- add `RateLimitedPsychicJob` (exported from `@rvoh/psychic-workers/errors`). Throw `new RateLimitedPsychicJob({ pauseQueueForSeconds })` from inside a backgrounded or scheduled method when the outside service it talks to rate limits the request (an HTTP 429, say). The value is a number of seconds, the same unit as HTTP's `Retry-After` header, so a header value can be passed straight through. When the worker running the job carries a BullMQ `limiter` — a named workstream with `rateLimit`, a native `namedQueueWorkers` entry with `limiter`, `nativeBullMQ.defaultWorkerOptions.limiter`, or a global `defaultBullMQWorkerOptions.limiter` — the pause is logged at `warn` (`[psychic-workers] pausing queue <name> for <seconds>s: a job threw RateLimitedPsychicJob` — the length comes from the job and is applied as given; psychic-workers does not cap it, beyond the validation of `pauseQueueForSeconds` described below), the queue is paused for that many seconds, and the job goes back onto the queue (`prioritized`, since psychic-workers writes a priority on every job it enqueues; see the note on stalled jobs below for the one other way a psychic job reports `waiting`) with `attemptsMade` unchanged and no backoff, so a burst is not multiplied by the exponential retry schedule. The check reads only the worker options: a queue rate-limited solely through BullMQ's `queue.setGlobalRateLimit` does not qualify and is treated as misconfigured (next bullet). Every worker on that queue that carries a `limiter` honors the pause; a limiter-less worker in another process on the same queue (during a rolling deploy, say) re-fetches and re-runs the job once instead. The pause replaces the queue's current limiter window and counter — the configured `rateLimit` window and any earlier pause alike — so once it elapses up to `max` jobs may start at once, and a pause shorter than the remaining window shortens the configured limit; concurrent throws overwrite each other (last writer wins). Once the pause ends the re-queued job is fetched first — first in ordering, which is not the same as immediately. BullMQ pushes a job that carries a priority back from `active` with a bare sorted-set write and no marker, where a priority-less job's push back adds one, so the re-queued job wakes no worker that is already blocked waiting for work. The worker counting down the pause it was just handed picks the job up as soon as the pause elapses; an idle worker on the same queue in another process — the "limiter-less worker in another process" case above — may not notice it until its blocking read times out, bounded by BullMQ's `drainDelay` (5s by default). Latency only: nothing is stranded, and the pause the job itself asked for usually exceeds that window. A request that never clears pauses the queue again every cycle; each re-fetch counts in BullMQ's `attemptsStarted`, and the worker option `maxStartedAttempts` (e.g. `defaultBullMQWorkerOptions: { maxStartedAttempts: 10 }`) is the only bound — without it the cycle is unbounded, so set it on any workstream whose jobs throw the signal. `pauseQueueForSeconds` must be a positive, finite number of safe magnitude; the constructor throws a `RangeError` otherwise, at the throw site, so a nonsense value fails there rather than at the pause. The bound is on the value in seconds; the queue is paused for that value in milliseconds, which Redis accepts across the whole legal range — only at the very top of it is the product past `Number.MAX_SAFE_INTEGER` and so not exactly the number asked for, at a pause length of roughly 285 million years. A fractional number of seconds is legal and is rounded **up** to a whole second before the queue is paused — the field is a lower bound on the pause, so overshooting it by under a second cannot break the promise, while rounding down could.
- throwing `RateLimitedPsychicJob` from a job whose worker carries no `limiter` is a misconfiguration: the queue cannot be paused, so the job fails normally (retried on the queue's `attempts`/backoff schedule, one `failed` event per attempt) with an error class this package does not export, whose message names the fix for the configuration mode in use (simple mode: a named workstream with `rateLimit`; native BullMQ mode: `limiter` on the queue's `namedQueueWorkers` entry, or moving the job to a named queue that has one). psychic-workers registers no `failed` listener, so the failure is observable through the application's own failed-job monitoring. The same check runs under test invocation (`testInvocation: 'automatic'`) and the `WorkerTestUtils` helpers, so a misplaced job goes red in specs: `WorkerTestUtils.work()` and `workScheduled()` reject with the misconfiguration error, and on a queue whose workers do carry a `limiter`, `RateLimitedPsychicJob` propagates untranslated so a spec can assert on it, with `work()` stopping at the first one (the job back in the queue — `prioritized` — no attempt counted) rather than looping.
- `Background` gains a public method, `misconfiguredRateLimitSignal(err, queue)`. It is the check described in the two bullets above, factored out so that the worker processors, test invocation and `WorkerTestUtils` all answer "may a job on this queue signal `RateLimitedPsychicJob`?" the same way: given an error and one of `background.queues`, it returns the misconfiguration error to fail the job with when the error is a `RateLimitedPsychicJob` on a queue whose workers carry no `limiter`, and `undefined` otherwise. It is `public` because `WorkerTestUtils` calls it across a module boundary, and it ships in the type declarations, so it is additive public surface — but it is package plumbing, not an API to build on, and it may change. Its return is typed as `Error | undefined` rather than as the concrete class, which this package does not export.
- maintenance: remove the duplicate declaration of `PsychicBackgroundWorkstreamOptions`, which was declared twice, byte for byte, and merged. The public type is unchanged.
- maintenance: expand the TSDoc for `connect`, `queues` / `defaultQueueName`, and `workerCount` / `nativeBullMQ.defaultWorkerCount` / `concurrency` — who calls `connect` automatically, how the Redis queue name is derived from the name you configured (so inspecting Redis for the configured name finds nothing under it), and how many workers exist and how many jobs run at once in each configuration mode, including that the simple mode forces a concurrency of ten where the native mode uses one. Comments only; no behaviour change.

## 2.6.0

Unscheduling stops future runs; it does not cancel a run already placed on a queue.

## 2.4.1

- fix: `WorkerTestUtils.clean()` now also clears delayed jobs, as its documentation always stated. `queue.drain()` defaults to leaving the delayed set alone, and BullMQ parks a failed job there while it awaits its retry, so a job failing for a non-transient reason (a `globalName` that no longer resolves, say) was unreachable by `clean()` and survived into later test files — with the default `attempts`/backoff, for days. `WorkerTestUtils.workScheduled()` reads `getDelayed()` indiscriminately, so such a job would then fail whichever spec called `workScheduled` next, in a file unrelated to whatever enqueued it.
